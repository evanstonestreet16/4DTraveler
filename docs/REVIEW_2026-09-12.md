## P0 — Blocks the demo or the release gates

### P0-1 Every Playwright spec lost its entry point

**Owner:** WS2 (path) + WS4 (suite). **Cause:** `ab2dd3d` removed the `curated-city-links` nav from `LocationSelector`.

All 13 specs entered the app by clicking one of those pills: `getByRole('button', { name: /Kyoto/ })`, `/Italy.*Rome/`, or `/Pennsylvania, United States Pittsburgh/`. Those buttons no longer exist. `tests/exploration.spec.ts` is the only spec that does not use a pill, and it is stale for a different reason: it clicks the canvas center expecting Pittsburgh, but `heroCity` now resolves to Rome.

There is no drop-in selector replacement, because pins only enter the DOM after a pointer hover on their country polygon.

Two options, in order of preference:

1. Add a test-and-demo entry query param (`/?location=rome-125&era=125-ce`) read once in `AppProvider`. This also delivers the deep-linking that `docs/workstream2.md` section 1 lists as in-scope and never built, and it makes the demo recoverable if the globe misbehaves on stage.
2. Add a shared `enterCity(page, 'Rome')` helper that hovers the country polygon, waits for the pin, then clicks it. Slower and flakier, but it exercises the real path.

### P0-2 No keyboard or pointerless path into any world

**Owner:** WS2. **Cause:** same commit. Pre-existing gap that the deleted pill list was covering.

Pins are created only when `onPolygonHover` sets `pinnedIso`, so with no pointer movement the globe has zero focusable children. The globe container is a `role="group"` div. A keyboard-only user cannot reach Rome, Kyoto, or the era selector.

The comment at `src/components/location/globe/GlobeView.tsx:109` claims the pins are "keyboard reachable". That is true of the elements and false of the flow.

`docs/workstream2.md` section 8 already records this as "a regression to close, not a nice-to-have". Restoring a visible list of curated destinations beside the globe closes it and doubles as the touch answer in section 7.

Touch is in better shape than expected and does not need separate work: `three-render-objects` listens on `pointerdown` as well as `pointermove` (`node_modules/three-render-objects/dist/three-render-objects.mjs:520`), so a tap on Italy spawns the Rome pin and a second tap enters. It is undiscoverable, not broken.

### P0-3 The object panel renders no authored content and needs a local server

**Owner:** WS3, with WS4 content impact. **Cause:** `cca4719` "Replace authored object notes with a Grok tour and live ticket links".

`ObjectInfoPanel` no longer renders `object.description`, `object.whyItMatters`, `object.confidence`, or `object.sources`. The panel body is a single "Grok tour" section (`src/components/info/ObjectInfoPanel.tsx:145`) fed by `POST /api/city-summary` with a 60-second timeout.

That endpoint exists only as a `server.proxy` entry in `vite.config.ts`, which applies to `npm run dev` only. Consequences:

- In `npm run dev` without the FastAPI process on `127.0.0.1:8000`, every object reads "Live summary is unavailable."
- In `npm run preview` or any deployment there is no proxy at all, so that failure is guaranteed.

All 18 reviewed Rome and Kyoto objects therefore show no historical content and no source references at the final step of the demo path. `AGENTS.md` states the Workstream 3 boundary explicitly: "the static information panel must remain usable without them." `PROJECT_STATUS.md` lists Grok integration as out of scope.

**Fix:** restore the authored prose and sources as the always-present panel body, and render the RAG answer as an additive section that is simply absent when the service is unreachable.

## P1 — Correctness and performance

### P1-1 Globe accessors are recreated every render, tearing down all pins

**Owner:** WS2. **File:** `src/components/location/globe/GlobeView.tsx`.

`react-kapsule` diffs props by identity and calls the underlying setter for anything that changed (`node_modules/react-kapsule/dist/react-kapsule.mjs:33`). Every accessor passed to `<Globe>` is an inline arrow, so all of them are re-set on every render:

- `htmlElement` changing runs `state.dataMapper.clear()` inside three-globe, which destroys and rebuilds every pin DOM element. This is the same observable failure as recorded defect #3 in `docs/workstream2.md` section 2 (pin unmounts from under the cursor), reintroduced through accessor identity rather than data identity.
- The polygon accessors have `triggerUpdate` enabled, so each render re-walks 242 features / 1608 polygon parts and re-subdivides the caps.

`useElementSize` compounds this: it calls `setSize` on every `ResizeObserver` entry with no equality check (`src/components/location/globe/useElementSize.ts:10`), so a window drag rebuilds all country geometry per frame.

**Fix:** hoist `htmlLat`/`htmlLng`/`htmlElementVisibilityModifier` to module scope, wrap `makePin` in `useCallback([])` (`dispatch` is stable), and key the colour/stroke accessors on `useCallback([hoveredIso])` so they change only when hover actually changes.

### P1-2 `mode: 'globe'` is unreachable, and its tree still ships

**Owner:** integration owner decision, then WS2.

Nothing dispatches `{ type: 'mode', mode: 'globe' }` any more. The only remaining reference is `src/app/App.tsx:74`, which can only fire when already in globe mode. So `showGlobe` (`App.tsx:22`) is permanently false and `isLandingGlobe` reduces to `!state.selectedLocationId`.

Unreachable as a result: `src/components/globe/` (`GlobeExperience`, `GlobeCanvas`, `cities.ts`, `latLon.ts`), `src/services/grok/`, and `src/services/procedural/`. It is still built and shipped: `dist/assets/GlobeExperience-D8uWNAqa.js`, 40.6 kB raw / 13.9 kB gzip.

Also stale as a result: the `.globe-cta` (`globals.css:1261`) and `.curated-city-links` (`globals.css:1294`) rules, the `EntryMode` doc comment in `src/app/state.ts` describing `catalog` as "the curated Pittsburgh path", and the grok/tripo dev proxies plus their `.env.example` keys.

This needs an owner decision rather than a unilateral delete, because `docs/workstream2.md` section 6 flagged the two-globe reconciliation as an open integration question and both globes landed anyway.

### P1-3 Pittsburgh is still reachable from the landing globe

**Owner:** WS2 + content.

`AGENTS.md` says Pittsburgh is legacy pending deletion and outside active scope, but `src/data/locations.ts` still gives it a `globe` anchor, so its pin is clickable and routes into the legacy primitive renderer. It is also the only clickable US pin, which makes the US the most inviting country on the globe.

Dropping the `globe` field from the Pittsburgh entry removes it from the globe without touching the rest of the legacy code, since clickability is derived from the curated locations list.

### P1-4 Landing globe CSS depends on the dead globe's rules

**Owner:** WS2. **File:** `src/styles/globals.css`.

`.globe-stage` is declared twice: line 113 (`position: relative`, `min-height: calc(100vh - 162px)`, `overflow: hidden`) and line 1299 (`display: grid`, two-column `grid-template-columns`, `margin-top: 28px`). The second block was written for the now-dead Grok globe page.

The landing screen works only because `.globe-stage.globe-landing` (line 1272) has higher specificity and overrides `display` and `margin-top`, and because `.globe-landing .globe-viewport` undoes the `min-height: 520px`, border, and shadow that line 1306 applies. Deleting `src/components/globe/` per P1-2 without untangling this will change the landing layout.

Two sizing bugs inside the same block:

- `min-height: calc(100vh - 89px)` (line 1275) hardcodes the 88px header plus its 1px border, but the `max-width: 640px` block drops `.site-header` to 72px, leaving roughly 16px of dead space on phones.
- `100vh` measures the layout viewport including collapsible mobile browser chrome, so the globe overflows the visible area on mobile Safari and Chrome. Use `100dvh`.

Separately, `.app-shell { max-width: 1600px; margin: auto }` puts light page gutters either side of the dark `#111a24` globe panel on wide monitors.

### P1-5 The landing screen gives no instruction

**Owner:** WS2. **Cause:** `ab2dd3d` hid the header tagline and the footer on the landing screen.

The globe is now presented bare, and hover-to-reveal-pins is the only way in. There is no visible text telling a visitor to hover or tap a country; the only hint is the container's `aria-label`. Combined with P0-2, a first-time visitor on any device has to guess.

The curated destination list from P0-2 solves discoverability and accessibility together.

## P2 — Polish and hygiene

### P2-1 `npm run lint` is red for unrelated reasons

`pano-explorer/scripts/generate-panoramas.mjs` has 4 `no-undef` errors (`process`, `console`, `Buffer`) because `eslint.config.js` does not apply Node globals to that directory. The lint gate in the `AGENTS.md` verification loop is therefore failing independently of any change under review.

### P2-2 No reduced-motion handling for the intro morph

`LocationSelector` gates the globe behind a fixed 2200ms timer, then crossfades with a 0.6s opacity/transform transition and a `scale(3.2)` on the logo. The only `prefers-reduced-motion` rule in `globals.css` targets the Tripo spinner. `CameraController` and `OverviewEraTransition` both respect the preference, so this is the one surface that does not. There is also no skip affordance.

### P2-3 The globe's opening camera depends on array order

`heroGlobe` in `GlobeView.tsx:26` is `locations.find((location) => location.globe)?.globe`, so reordering `src/data/locations.ts` silently moves the globe's initial point of view. It resolved to Pittsburgh when the comment in `tests/exploration.spec.ts:9` was written and resolves to Rome today. An explicit `hero: true` flag on the `Location` contract, or a named constant, makes it intentional.

### P2-4 Scene modules import JSON out of `public/`

`src/data/worlds/rome-125.scene.ts`, `rome-present.scene.ts`, and `kyoto-1700.scene.ts` import manifests and metrics via relative paths into `public/`. The dev server warns on each one ("Assets in public directory cannot be imported from JavaScript") and the files end up in `dist/` twice: copied verbatim, and inlined into `dist/assets/index-*.js`.

It builds and runs, so this is noise plus a few duplicated kilobytes. Moving the manifests under `src/data/` removes both.

### P2-5 The entry chunk carries every world's data

`src/data/locations.ts` imports all five worlds, and `App.tsx` imports `locations`, so the landing screen eagerly pays for Rome, Rome Present, Kyoto, and both Pittsburgh scene and content modules (`dist/assets/index-*.js`, 247.7 kB raw / 79.5 kB gzip). Only the renderer is behind the lazy boundary, not the data.

A `locations` list holding ids, names, and eras, with world modules resolved lazily at `enterWorld`, would move most of that behind the same boundary.

### P2-6 Landing screen payload

`dist/assets/GlobeView-*.js` is 1762.9 kB raw / 558.3 kB gzip, carrying three-globe, d3, and the 189 kB gzip `countries.json`. This is consistent with the ~649 kB gzip figure recorded in `docs/workstream2.md` section 4.1, so it is not a regression, but it is the blocking cost of the first screen and the 2.2s logo intro is the only thing covering it. Worth a decision rather than a fix: a lower-resolution country bake for first paint, or accepting it.

### P2-7 Stale copy

`index.html`'s meta description still reads "Explore Pittsburgh in 1892 through an interactive historical 3D world."

## Specification drift

These documents contradict each other and the code. Reconciling them is cheap and prevents the next contributor from re-deriving the above.

`docs/workstream2.md` is the most out of date file in the repo:

- Section 2 says the only curated `Location` is Pittsburgh. There are three, and Rome is first.
- Section 6 describes the two-globe conflict as unresolved and states "both must not land". Both landed; see P1-2.
- Section 9 says five specs need repointing. It is now all 13, for a different cause; see P0-1.
- Section 10 lists phases 5 to 7 as remaining. Phase 5 changed shape, phase 6 is arguably obsolete (see below), phase 7 regressed.

Phase 6 ("loading progress and retry UX for heavy GLB loads") should probably be closed as no-longer-needed rather than done. Rome and Kyoto load images, not GLBs, and `OverviewEraTransition` and `RenderedCityViewer` already own their retry affordances. The remaining gap is the Pittsburgh GLB path, which is being deleted.

`AGENTS.md` and `PROJECT_STATUS.md` list Grok, MongoDB, and ElevenLabs as out of scope, while `services/grok` is dead code in the bundle, `services/tripo` is wired into `WorldScene`, and `services/cityRetrieval` is the sole content source for the object panel. Either the scope statement or the code needs to move.
